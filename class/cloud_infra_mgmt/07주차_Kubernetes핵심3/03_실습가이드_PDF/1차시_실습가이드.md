# 7주차 1차시 실습가이드
## Ingress 개념

## 개요

지금까지 NodePort로 외부에서 서비스에 접속하는 법을 배웠습니다. 그런데 서비스가 블로그, 쇼핑몰,
API처럼 여러 개라면 포트 번호를 하나하나 관리하기가 번거로워집니다. 오늘은 여러 서비스를 하나의
진입점으로 묶어주는 K8s 오브젝트, **Ingress**의 개념과 구조를 배우고, Ingress 컨트롤러를 켜서
동작을 확인합니다.

- 소요시간: 15분(Killercoda) + 5분(개인 VM 과제)
- **오늘은 여기까지만 합니다**: 실제 라우팅 규칙 작성과 도메인 접속은 다음 2차시에 진행합니다.
  오늘은 Ingress 컨트롤러를 설치하고 Ingress 리소스의 구조를 확인하는 것까지만 합니다.

## Part A. Killercoda 실습

LMS > 7주차 > `05_Killercoda_링크` > `1차시_링크.md`에 안내된 URL로 접속한 뒤 아래 순서대로
진행하세요.

> **참고: 이 Killercoda 환경은 개인 VM(minikube)과 설치 명령어가 다릅니다**
>
> 개인 VM은 minikube라서 `minikube addons enable ingress` 한 줄로 끝나지만, 이 Killercoda
> 환경은 실제 kubeadm 클러스터라 minikube 자체가 없습니다. 그래서 여기서는 같은 역할을 하는
> ingress-nginx 컨트롤러를 매니페스트로 직접 설치합니다. **명령어는 다르지만 "Ingress
> 컨트롤러를 켠다"는 목적과 결과는 동일**하니 헷갈리지 마세요. 개인 VM 과제(Part B)에서는 이
> 설치 명령이 아니라 `minikube addons enable ingress`를 그대로 사용합니다.

이 세션은 **60분 제한**이 있습니다. 실습 중 시간이 종료되어도 당황하지 말고, LMS 링크로 다시
접속해 이어서 진행하면 됩니다.

### Step 1. Ingress 컨트롤러 설치

강의에서는 개인 VM(minikube) 기준으로 `minikube addons enable ingress` 한 줄이면 Ingress
컨트롤러가 켜집니다. 이 Killercoda 환경은 minikube가 아니라 실제 kubeadm 클러스터이므로, 같은
역할을 하는 ingress-nginx 컨트롤러를 매니페스트로 직접 설치합니다. 컨트롤러 자체(무엇을 켜는지)는
강의에서 배운 것과 동일합니다.

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.3/deploy/static/provider/baremetal/deploy.yaml
```

**실행 결과 예시**

```
namespace/ingress-nginx created
serviceaccount/ingress-nginx created
...
deployment.apps/ingress-nginx-controller created
```

여러 리소스(Namespace, ServiceAccount, ConfigMap, Deployment 등)가 한 번에 생성되었다는 메시지가
쭉 나오면 정상입니다. 컨트롤러 Pod가 실제로 뜨기까지는 시간이 좀 걸리니, 다음 단계에서 상태를
확인합니다.

### Step 2. 컨트롤러 Pod 상태 확인

`kubectl get pods -n ingress-nginx`로 방금 설치한 컨트롤러 Pod가 정상적으로 떠 있는지
확인합니다. (`-n`은 namespace를 지정하는 옵션으로, ingress-nginx는 별도의 namespace에
설치됩니다.)

```bash
kubectl get pods -n ingress-nginx
```

**실행 결과 예시**

```
NAME                                        READY   STATUS      RESTARTS   AGE
ingress-nginx-admission-create-xxxxx        0/1     Completed   0          40s
ingress-nginx-admission-patch-xxxxx         0/1     Completed   0          40s
ingress-nginx-controller-7d9f8c6b5d-abcde   1/1     Running     0          40s
```

`ingress-nginx-controller-...` Pod의 STATUS가 `Running`이면 성공입니다. 아직
`ContainerCreating`이라면 몇십 초 기다렸다가 같은 명령을 다시 실행해보세요. `admission-create`,
`admission-patch` Pod는 설치 과정에서 한 번 실행되고 끝나는 Job이라 STATUS가 `Completed`인 것이
정상입니다.

### Step 3. Ingress 리소스 구조 확인

`kubectl explain`은 어떤 K8s 리소스가 어떤 필드로 구성되어 있는지 문서 없이 터미널에서 바로 확인할
수 있는 명령어입니다. Ingress 리소스가 어떤 구조인지 살펴봅니다.

```bash
kubectl explain ingress
```

**실행 결과 예시**

```
KIND:     Ingress
VERSION:  networking.k8s.io/v1

DESCRIPTION:
     Ingress is a collection of rules that allow inbound connections to reach
     the endpoints defined by a backend...

FIELDS:
   apiVersion   <string>
   kind <string>
   metadata     <Object>
   spec <Object>
   status       <Object>
```

`spec` 필드 안에 오늘 배운 라우팅 규칙(`rules`)이 들어갑니다. `kubectl explain ingress.spec`을
이어서 실행해보면 `rules`, `tls` 같은 하위 필드도 볼 수 있습니다. 오늘은 이렇게 구조를 확인하는
것까지만 하고, 실제로 이 필드들을 채운 YAML을 작성해서 적용하는 것은 다음 2차시에 진행합니다.

## Part B. 개인 VM 실습

개인 VM에서도 Ingress 컨트롤러를 활성화합니다. minikube 환경에서는 Part A의 매니페스트 설치 명령
대신, minikube 전용 addon 명령 한 줄이면 됩니다.

```bash
minikube addons enable ingress
```

컨트롤러 Pod가 완전히 준비되기까지 시간이 좀 걸릴 수 있습니다. 아래 명령으로 STATUS가 `Running`이
될 때까지 기다리세요.

```bash
kubectl get pods -n ingress-nginx
```

STATUS가 `Running`이 된 화면을 캡처해서 제출하시면 됩니다.

> **왜 Killercoda와 명령어가 다른가요?**
> Killercoda 환경은 minikube가 없는 실제 kubeadm 클러스터라 addon 기능 자체를 쓸 수 없어서
> 매니페스트로 직접 설치했습니다. 개인 VM은 minikube이므로 addon 기능을 그대로 쓰면 됩니다.
> 명령어만 다를 뿐, "Ingress 컨트롤러를 활성화한다"는 목적과 결과는 동일합니다.

다음 2차시에는 오늘 활성화한 이 컨트롤러를 이용해 실제 도메인 주소로 접속하는 실습을 합니다.
