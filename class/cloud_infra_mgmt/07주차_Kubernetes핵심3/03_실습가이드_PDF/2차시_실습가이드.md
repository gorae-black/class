# 7주차 2차시 실습가이드
## Ingress 라우팅 규칙 실습

## 개요

지난 1차시에서 Ingress가 무엇인지 배우고 컨트롤러까지 켜봤습니다. 오늘은 실제로 Ingress YAML을
작성해서 라우팅 규칙을 만들고, 규칙에 따라 서로 다른 서비스로 요청이 갈라지는 것을 직접 확인합니다.

- 소요시간: 15분(Killercoda) + 5분(개인 VM 과제)
- Ingress YAML의 핵심은 `rules` 항목입니다. 이 아래에 `host`(도메인)나 `path`(경로)별로 라우팅
  규칙을 나열하고, 각 규칙의 `backend`에 연결할 Service 이름과 포트를 지정합니다. Ingress는 직접
  Pod에 연결하지 않고, 항상 Service를 거쳐서 연결됩니다 — 5주차에서 배운 그 Service입니다.

## Part A. Killercoda 실습

LMS > 7주차 > `05_Killercoda_링크` > `2차시_링크.md`에 안내된 URL로 접속한 뒤 아래 순서대로
진행하세요.

> **참고: 이 Killercoda 환경은 개인 VM(minikube)과 실습 방식이 다릅니다**
>
> 1차시와 같은 이유로, 여기서는 컨트롤러를 kubeadm용 매니페스트로 다시 설치합니다(Step 1).
> 또한 오늘 Killercoda 실습은 **경로(path) 기반 라우팅**(`/ko`, `/en`)으로 진행하지만, 개인 VM
> 과제(Part B)는 **도메인(host) 기반 라우팅**(`myapp.local`을 hosts 파일에 매핑)으로 진행합니다.
> 방식은 다르지만 "Ingress가 규칙에 따라 요청을 알맞은 Service로 분배한다"는 핵심 원리는
> 동일합니다.

이 세션은 **60분 제한**이 있습니다. 실습 중 시간이 종료되어도 당황하지 말고, LMS 링크로 다시
접속해 이어서 진행하면 됩니다.

### Step 1. Ingress 컨트롤러 재설치

이 Killercoda 환경은 세션을 새로 시작할 때마다 깨끗한 상태로 초기화되므로, 지난 1차시에 설치했던
Ingress 컨트롤러를 다시 설치합니다.

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.3/deploy/static/provider/baremetal/deploy.yaml
```

컨트롤러 Pod가 준비될 때까지 잠시 기다린 후, 아래 명령으로 STATUS가 `Running`인지 확인합니다.

```bash
kubectl get pods -n ingress-nginx
```

**실행 결과 예시**

```
NAME                                        READY   STATUS      RESTARTS   AGE
ingress-nginx-controller-7d9f8c6b5d-abcde   1/1     Running     0          45s
```

`ingress-nginx-controller-...` Pod가 `Running`이 되면 다음 단계로 넘어갑니다.

### Step 2. 경로별 백엔드 앱 준비

Ingress로 경로를 나눠 연결할 대상이 필요합니다. `/ko` 경로용, `/en` 경로용으로 서로 다른 응답을
돌려주는 간단한 앱을 `hashicorp/http-echo` 이미지로 각각 구성합니다.

```bash
kubectl create deployment ko-app --image=hashicorp/http-echo -- -text="안녕하세요, 한국어(ko) 서비스입니다"
kubectl expose deployment ko-app --port=80 --target-port=5678

kubectl create deployment en-app --image=hashicorp/http-echo -- -text="Hello, this is the English (en) service"
kubectl expose deployment en-app --port=80 --target-port=5678
```

**실행 결과 예시**

```
deployment.apps/ko-app created
service/ko-app exposed
deployment.apps/en-app created
service/en-app exposed
```

`kubectl get pods`로 `ko-app`, `en-app` Pod가 각각 `Running` 상태인지 확인하고 다음 단계로
넘어가세요.

### Step 3. 경로 기반 Ingress 작성

`/ko`로 오는 요청은 `ko-app`으로, `/en`으로 오는 요청은 `en-app`으로 보내는 Ingress YAML을
작성합니다.

```bash
cat <<'EOF' > ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: path-routing-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /ko
        pathType: Prefix
        backend:
          service:
            name: ko-app
            port:
              number: 80
      - path: /en
        pathType: Prefix
        backend:
          service:
            name: en-app
            port:
              number: 80
EOF
kubectl apply -f ingress.yaml
```

**실행 결과 예시**

```
ingress.networking.k8s.io/path-routing-ingress created
```

`kubectl get ingress`로 방금 만든 `path-routing-ingress`가 목록에 보이는지 확인하세요. `rules`
아래 `/ko`, `/en` 두 경로가 각각 다른 `backend` Service를 가리키고 있다는 점이 오늘 실습의
핵심입니다.

### Step 4. 경로별 접속 확인

Ingress 컨트롤러는 NodePort로 노출되어 있으므로, 그 포트로 `/ko`, `/en` 경로를 각각 요청해서 정말
다른 응답이 오는지 확인합니다.

```bash
NODE_PORT=$(kubectl get svc -n ingress-nginx ingress-nginx-controller -o=jsonpath='{.spec.ports[0].nodePort}')
curl http://localhost:$NODE_PORT/ko
curl http://localhost:$NODE_PORT/en
```

**실행 결과 예시**

```
안녕하세요, 한국어(ko) 서비스입니다
Hello, this is the English (en) service
```

같은 주소, 같은 포트로 요청했는데 경로(`/ko` vs `/en`)만 다르게 줬을 뿐인데 완전히 다른 응답이
왔습니다. 이게 바로 Ingress의 경로 기반 라우팅입니다 — path 규칙에 따라 요청이 서로 다른 Service,
서로 다른 Pod로 갈라져 처리된 것입니다.

## Part B. 개인 VM 실습

개인 VM에서는 Killercoda와 달리 **도메인(host) 기반 라우팅**으로 실습합니다. 원래 우리가 아는
도메인 주소는 DNS 서버가 실제 IP 주소로 변환해줘야 접속이 됩니다. 그런데 hosts 파일에 '도메인 -
IP' 짝을 직접 적어두면, DNS 조회 없이 그 IP로 바로 연결됩니다.

### 1단계. hosts 파일에 도메인 매핑

`myapp.local`이라는 가짜 도메인을 minikube의 IP에 매핑합니다.

```bash
echo "$(minikube ip) myapp.local" | sudo tee -a /etc/hosts
```

이때 VM 계정 비밀번호를 입력해야 합니다. 맨 아래에 한 줄만 추가하는 것이라 기존 설정에는 영향이
없습니다.

### 2단계. host 기반 Ingress 작성

`myapp.local`을 host로 지정하는 `ingress.yaml`을 작성하고 적용합니다. (연결할 Service 이름·포트는
수업 중 사용한 자신의 서비스에 맞게 채워 넣으세요.)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
spec:
  rules:
  - host: myapp.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: myapp-service
            port:
              number: 80
```

```bash
kubectl apply -f ingress.yaml
```

### 3단계. 도메인 주소로 접속 확인

```bash
curl http://myapp.local
```

접속에 성공한 화면을 캡처해서 제출하시면 됩니다.

> **한 가지 짚고 넘어갈 점**
> 실제 서비스는 공인 DNS 서버에 도메인을 등록해서 전 세계 어디서든 접속할 수 있게 합니다. 하지만
> 오늘 우리는 내 VM의 hosts 파일만 수정한 것이라, 이 도메인은 **내 VM 안에서만** 동작합니다. 다른
> 컴퓨터에서는 `myapp.local`을 쳐도 연결되지 않습니다. 그래도 Ingress가 도메인을 보고 라우팅을
> 처리하는 원리 자체는 완전히 동일합니다. hosts 매핑은 그 원리를 배우기 위한 '로컬 실습용
> 흉내'입니다.

> **왜 Killercoda(경로 기반)와 VM(도메인 기반) 실습 방식이 다른가요?**
> hosts 매핑은 "도메인 이름"을 IP로 바꿔주는 역할일 뿐이고, Ingress가 요청을 보고 라우팅을
> 판단하는 원리(host든 path든)는 동일합니다. 오늘 Killercoda에서 배운 경로 기반 라우팅에 호스트
> 기반 라우팅을 얹은 것이 VM 실습이라고 생각하면 됩니다.

**curl이 안 될 때 확인할 것**
- hosts 파일에 매핑이 제대로 저장됐는지(`cat /etc/hosts`로 확인)
- Ingress 컨트롤러 Pod가 Running 상태인지
- `ingress.yaml`의 host 값과 curl 주소가 정확히 일치하는지
