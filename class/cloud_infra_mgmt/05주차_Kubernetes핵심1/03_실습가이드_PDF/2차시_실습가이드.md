# 5주차 2차시 실습가이드
## Service 타입 비교와 NodePort 실습

## 개요

지난 1차시에서 "Pod IP가 불안정하다"는 문제를 확인했습니다. 오늘은 그 해결책인 **Service**를 실제로
만들어서 우리 앱에 접속해보겠습니다. Service에는 ClusterIP, NodePort, LoadBalancer 세 가지 타입이
있는데, 오늘은 그중 **NodePort**로 실습합니다. LoadBalancer는 AWS·GCP 같은 실제 클라우드 사업자가
있어야 동작하는데, 우리가 쓰는 로컬/실습 환경(minikube, Killercoda)에는 그런 로드밸런서가 없기
때문입니다. NodePort는 로컬 환경에서도 외부 접속을 흉내낼 수 있는 실습용 대안입니다 — 실무 운영
환경의 표준은 LoadBalancer라는 점을 기억해두세요.

- 소요시간: 개념 설명 25분 + Killercoda 실습 15분 + VM 과제 안내 5분 + 결과 제출 5분 (총 50분)
- 오늘의 핵심: ClusterIP(내부) / NodePort(로컬 테스트용 외부) / LoadBalancer(운영용 외부)로 나뉜다.
  로컬 minikube 환경에서는 NodePort로 외부 접속을 실습한다.

## Part A. Killercoda 실습

LMS > 5주차 > `05_Killercoda_링크`에 있는 2차시 링크로 접속한 뒤, 아래 순서대로 진행하세요.

> **참고**: 이 Killercoda 환경은 매번 새로 시작되는 클러스터입니다. 그래서 먼저 지난 시간에
> 만들었던 `myapp` Deployment를 다시 만드는 것부터 시작합니다.
>
> 이 세션에는 **60분 제한**이 있습니다. 실습 중 시간이 종료되어도 당황하지 마세요 — 오늘 실습은
> 짧게 끝나므로 문제 없지만, 만약 중간에 끊기면 LMS의 링크로 다시 접속해 이어서 진행하면 됩니다.

### Step 1. myapp Deployment 다시 만들기 (복습)

지난 1차시와 같은 `myapp` Deployment를 다시 만듭니다. `apiVersion`은 `apps/v1`, `kind`는
`Deployment`, 이름은 `myapp`, `replicas`는 2, 이미지는 `nginx`입니다.

```
cat <<EOF > deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: nginx
        image: nginx
EOF
kubectl apply -f deployment.yaml
```

**실행 결과 예시**

```
deployment.apps/myapp created
```

Pod 2개가 Running 상태가 될 때까지 잠시 기다린 뒤 다음 단계로 진행하세요 (`kubectl get pods`로
확인 가능합니다).

### Step 2. NodePort Service 만들기

`kubectl expose`로 `myapp` Deployment에 NodePort 타입 Service를 연결합니다. `--type=NodePort`는
클러스터 밖에서도 접속할 수 있게 하라는 뜻이고, `--port=80`은 Service가 받을 포트입니다.

```
kubectl expose deployment myapp --type=NodePort --port=80
```

**실행 결과 예시**

```
service/myapp exposed
```

이제 `myapp`이라는 이름의 Service가 생겼고, 이 Service가 라벨(`app: myapp`)을 통해 뒤에 있는 Pod
2개를 자동으로 찾아 연결합니다.

### Step 3. 할당된 포트 번호 확인하기

`kubectl get svc myapp`으로 방금 만든 Service의 상세 정보를 확인합니다. NodePort는 30000~32767
범위에서 자동으로 할당되므로, 실행할 때마다 포트 번호가 다르게 나올 수 있습니다.

```
kubectl get svc myapp
```

**실행 결과 예시**

```
NAME    TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
myapp   NodePort   10.96.123.45   <none>        80:31234/TCP   10s
```

`PORT(S)` 칸의 `80:31234/TCP`에서 뒤에 있는 숫자(`31234`)가 외부에서 접속할 때 쓸 NodePort
번호입니다. 이 번호는 여러분 환경에서 다르게 나올 수 있으니, 실제로 출력된 번호를 다음 단계에서
그대로 사용하세요.

### Step 4. curl로 접속 확인하기

이 Killercoda 클러스터는 노드가 하나뿐이므로, 이 노드 자신에게 `localhost`와 방금 확인한 NodePort
번호로 curl을 보내면 바로 접속됩니다. 아래 `{NodePort 번호}` 자리에 앞 단계에서 확인한 숫자를 넣어
실행하세요.

```
curl localhost:{NodePort 번호}
```

**실행 결과 예시**

```
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
...
<h1>Welcome to nginx!</h1>
...
</html>
```

nginx 기본 환영 페이지 HTML이 출력되면 성공입니다. Pod의 IP를 전혀 몰라도, Service가 알아서 뒤에
있는 Pod 중 하나로 요청을 전달해준 것입니다 — 1차시에서 확인했던 "Pod IP가 계속 바뀌는" 문제가
Service 덕분에 더 이상 문제가 되지 않는다는 것을 직접 확인한 셈입니다.

여기까지가 오늘의 Killercoda 실습입니다. 수고하셨습니다!

## Part B. 개인 VM 실습

개인 로컬 VM(cloud-lab)에서 Killercoda와 동일한 명령어를 그대로 실행합니다.

1. 클러스터를 켜고, `myapp` Deployment가 떠 있는지 확인합니다(지난 1차시 실습에서 지우지 않았다면
   그대로 남아 있을 것입니다).

   ```
   minikube start
   kubectl get deployment myapp
   ```

2. NodePort Service를 만듭니다.

   ```
   kubectl expose deployment myapp --type=NodePort --port=80
   kubectl get svc myapp
   ```

3. minikube는 Killercoda와 달리 `localhost`로 바로 접속되지 않을 수 있으므로, `minikube service`
   명령으로 접속 가능한 전체 URL을 확인합니다.

   ```
   minikube service myapp --url
   ```

4. 확인한 URL로 curl 접속을 시도합니다.

   ```
   curl $(minikube service myapp --url)
   ```

   nginx 기본 페이지 HTML이 출력되면 성공입니다.

**다음 차시 예고**: 3차시에서는 Service가 실제로 어떤 Pod들과 연결되어 있는지 Endpoints로 확인하고,
여러 Pod로 트래픽이 고르게 나뉘어 전달되는 라운드로빈을 직접 확인해봅니다.
