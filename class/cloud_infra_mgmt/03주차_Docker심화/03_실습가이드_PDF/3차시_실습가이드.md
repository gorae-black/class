# 3주차 3차시 실습가이드

## 개요

3주차 마지막 시간입니다. 지난 2차시에서 여러분만의 Flask 앱을 `Dockerfile`로 빌드했습니다.
그런데 코드를 한 글자만 고쳐도 매번 빌드가 오래 걸린다면 불편하겠죠? 오늘은 그 빌드 속도를 확
줄이는 방법, **레이어 캐싱**을 배우고 직접 체감해봅니다. `Dockerfile`의 각 줄은 하나의
'레이어'가 되어 저장되는데, 다시 빌드할 때 바뀌지 않은 앞부분의 레이어는 그대로 재사용(캐시)하고,
중간에 바뀐 줄이 있으면 그 아래에 있는 레이어는 전부 다시 만들어야 합니다. 그래서 자주 안 바뀌는
것(라이브러리 설치)을 위쪽에, 자주 바뀌는 것(내 코드 COPY)을 아래쪽에 두는 것이 좋습니다. 이어서
`.dockerignore`로 불필요한 파일을 빌드에서 제외하는 방법도 배웁니다. 소요시간은 개념 설명 25분 +
Killercoda 실습 15분 + VM 과제 안내 5분 + 결과 제출 5분입니다.

**이 실습은 이번 주차 정식 VM 과제입니다.** 레이어 순서 변경 전/후 빌드 시간 비교 결과와
`.dockerignore` 적용 확인은 필수 제출물이며, Docker Hub push는 선택 심화 과제입니다.

## Part A. Killercoda 실습

LMS > 3주차 > 3차시 > `05_Killercoda_링크`의 URL로 접속한 뒤 아래 순서대로 진행하세요.

> 이 세션은 **60분 제한**이 있습니다. 실습 중 시간이 종료되어도 당황하지 마세요 — 만약 중간에
> 끊기면 LMS의 링크로 다시 접속해 이어서 진행하면 됩니다.

**[1] '나쁜' 순서 Dockerfile 준비하기**

지난 2차시에 만들었던 Flask 앱을 이 Killercoda 환경에 다시 준비합니다. 작업 폴더를 만들고
이동합니다.

```
mkdir ~/myflask && cd ~/myflask
```

```
cat <<'EOF' > app.py
from flask import Flask

app = Flask(__name__)

@app.route('/')
def hello():
    return 'Hello, Cloud!'

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
EOF
```

이번엔 일부러 '나쁜' 순서로 `Dockerfile`을 작성합니다. `COPY app.py .`를
`RUN pip install flask`보다 먼저 쓴 버전입니다.

```
cat <<'EOF' > Dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY app.py .
RUN pip install flask
EXPOSE 5000
CMD ["python", "app.py"]
EOF
```

`ls`로 두 파일이 준비됐는지 확인합니다.

```
ls
```

실행 결과 예시:

```
Dockerfile  app.py
```

두 파일이 준비됐다면, 이 '나쁜' 순서로 먼저 빌드해서 시간을 재보겠습니다.

**[2] 첫 빌드 시간 측정하기**

`time` 명령을 앞에 붙이면 명령어 실행에 걸린 시간을 알려줍니다. 이 '나쁜' 순서 `Dockerfile`로
첫 빌드를 하고 시간을 기록합니다.

```
time docker build -t myflask:bad .
```

실행 결과 예시:

```
[+] Building 13.4s (9/9) FINISHED
 => [1/4] FROM docker.io/library/python:3.11-slim
 => [2/4] WORKDIR /app
 => [3/4] COPY app.py .
 => [4/4] RUN pip install flask
 => exporting to image

real    0m13.482s
user    0m0.045s
sys     0m0.032s
```

`real` 줄이 실제로 걸린 시간입니다(네트워크 상태에 따라 숫자는 다를 수 있습니다). 이 숫자를
기억해두세요 — 다음 단계에서 비교할 기준값입니다.

**[3] 코드 수정 후 재빌드 — 캐시 효과 없음 확인**

이제 코드를 한 줄만 살짝 고쳐보겠습니다. 응답 문자열만 바꿔봅니다.

```
sed -i "s/Hello, Cloud!/Hello, Cloud! (updated)/" app.py
```

같은 '나쁜' 순서 `Dockerfile`로 다시 빌드하고 시간을 재봅니다.

```
time docker build -t myflask:bad .
```

실행 결과 예시:

```
[+] Building 12.9s (9/9) FINISHED
 => [1/4] FROM docker.io/library/python:3.11-slim
 => [2/4] WORKDIR /app
 => [3/4] COPY app.py .
 => [4/4] RUN pip install flask
 => exporting to image

real    0m12.951s
user    0m0.041s
sys     0m0.029s
```

빌드 출력에서 `CACHED` 표시 없이 `COPY app.py .`와 `RUN pip install flask` 두 줄이 다시 실제로
실행된 것을 확인하세요. `app.py`가 바뀌면서 `COPY` 레이어가 바뀌었고, 그 아래에 있는
`RUN pip install flask`까지 처음부터 다시 실행된 것입니다. `time` 결과도 이전 단계와 비슷하게
오래 걸렸을 것입니다 — 캐시의 이점을 전혀 못 본 것입니다.

**[4] '좋은' 순서로 바꿔서 캐시 효과 체감하기**

이번엔 `RUN`을 `COPY`보다 위로 옮긴 '좋은' 순서로 `Dockerfile`을 바꿔보겠습니다.

```
cat <<'EOF' > Dockerfile
FROM python:3.11-slim
WORKDIR /app
RUN pip install flask
COPY app.py .
EXPOSE 5000
CMD ["python", "app.py"]
EOF
```

순서를 바꾼 뒤 한 번 빌드해서 이 '좋은' 순서 기준의 레이어를 만들어둡니다.

```
time docker build -t myflask:good .
```

이제 다시 코드를 한 줄 고치고,

```
sed -i "s/updated/updated again/" app.py
```

같은 '좋은' 순서 `Dockerfile`로 다시 빌드해봅니다.

```
time docker build -t myflask:good .
```

실행 결과 예시:

```
[+] Building 1.1s (9/9) FINISHED
 => [1/4] FROM docker.io/library/python:3.11-slim
 => CACHED [2/4] WORKDIR /app
 => CACHED [3/4] RUN pip install flask
 => [4/4] COPY app.py .
 => exporting to image

real    0m1.187s
user    0m0.038s
sys     0m0.021s
```

`RUN pip install flask` 앞에 `CACHED`라고 붙어 있고, `real` 시간이 1~2초 수준으로 훨씬 짧아진
것을 확인하세요. 코드(`app.py`)만 바뀌었을 뿐 라이브러리 설치 과정은 그대로 캐시를 재사용했고,
바뀐 `COPY` 레이어부터만 새로 실행되었기 때문입니다. 순서만 바꿨을 뿐인데 빌드 속도가 확연히
빨라진 것을 직접 체감하셨을 겁니다.

**[5] .dockerignore 적용하기**

`.dockerignore`는 Git을 써보신 분이라면 익숙할 `.gitignore`와 비슷합니다. 빌드할 때 이미지
안에 넣지 않을 파일이나 폴더를 지정합니다. 예를 들어 `__pycache__/`, `.git/`, `*.log` 같은
파일은 굳이 이미지에 들어갈 필요가 없습니다. 특히 `COPY . .`처럼 폴더 전체를 통째로 복사할 때,
`.dockerignore`가 없으면 불필요한 파일까지 전부 이미지에 들어가버리니 꼭 챙겨야 합니다.

```
cat <<'EOF' > .dockerignore
__pycache__/
.git/
*.log
EOF
```

`cat .dockerignore`로 확인합니다.

```
cat .dockerignore
```

실행 결과 예시:

```
__pycache__/
.git/
*.log
```

한 번 더 빌드해서 정상적으로 반영되는지 확인합니다.

```
docker build -t myflask:good .
```

빌드가 평소처럼 문제 없이 끝나면, 다음 빌드부터는 `__pycache__`, `.git`, `*.log` 같은 파일이
있어도 이미지 안에 복사되지 않습니다. 이미지 용량도 줄고 빌드 속도도 빨라집니다.

**[6] (선택 심화) Docker Hub에 이미지 올리기**

여기부터는 **선택사항**입니다. 완성한 이미지를 Docker Hub에 올려서 다른 사람과 공유해보고
싶다면 해보세요. Docker Hub 계정이 있어야 진행할 수 있습니다.

먼저 `docker login`으로 Docker ID와 비밀번호를 입력해 로그인합니다.

```
docker login
```

본인 Docker ID를 이미지 이름 앞에 붙여서 다시 빌드합니다. `{여러분의dockerhub_id}` 자리에
실제 본인의 Docker ID를 넣으세요. (이미지 이름이 본인 Docker ID로 시작하지 않으면 push 권한
오류가 발생합니다.)

```
docker build -t {여러분의dockerhub_id}/myflask:v1 .
```

빌드가 끝나면 Docker Hub에 올립니다.

```
docker push {여러분의dockerhub_id}/myflask:v1
```

실행 결과 예시:

```
The push refers to repository [docker.io/{여러분의dockerhub_id}/myflask]
5f70bf18a086: Pushed
v1: digest: sha256:... size: 1234
```

Docker Hub 웹사이트(hub.docker.com)에 로그인해서 본인 저장소에 이미지가 올라갔는지 확인해보세요.
계정이 없거나 이 단계를 건너뛰어도 오늘 실습의 핵심(레이어 캐싱)은 이미 완료한 것이니 전혀
문제없습니다. 여기까지가 오늘의 Killercoda 실습입니다.

## Part B. 개인 VM 실습 (★ 필수 제출 / Docker Hub push는 선택)

개인 로컬 VM(`cloud-lab`)에서 위와 동일한 순서를 그대로 진행합니다.

1. VM에 접속합니다.

   ```
   multipass shell cloud-lab
   ```

2. Part A [1]~[5]와 동일하게 '나쁜' 순서 `Dockerfile`로 먼저 빌드 시간을 측정하고, 코드를
   한 줄 고친 뒤 다시 빌드해 캐시 효과가 없음을 확인합니다.

   ```
   time docker build -t myflask:bad .
   ```

3. `RUN`을 `COPY`보다 위로 옮긴 '좋은' 순서 `Dockerfile`로 바꾸고, 코드를 한 줄 고친 뒤 다시
   빌드해 `CACHED` 표시와 함께 빌드 시간이 훨씬 짧아지는 것을 확인합니다.

   ```
   time docker build -t myflask:good .
   ```

4. **'나쁜' 순서와 '좋은' 순서의 빌드 시간 비교 결과 화면을 캡처해둡니다.** 이 캡처가 필수
   제출물입니다.

5. `.dockerignore` 파일을 만들고 다시 빌드해서 정상 반영되는지 확인합니다.

   ```
   docker build -t myflask:good .
   ```

   `.dockerignore` 적용 확인 화면도 함께 캡처해둡니다.

6. (선택 심화) Docker Hub 계정이 있다면 `docker login` → 본인 ID를 붙인 이미지 재빌드 →
   `docker push`까지 진행하고, Docker Hub 저장소 확인 화면을 캡처해도 좋습니다. 완료하지
   않아도 괜찮습니다.

**생각해볼 질문**: 레이어 캐싱이 왜 빌드 속도를 높이는지 한 문장으로 설명할 수 있어야 합니다 —
자주 안 바뀌는 것을 위에, 자주 바뀌는 것을 아래에 두면 바뀐 부분 아래의 레이어만 다시 만들면
되기 때문입니다.

> 참고: 가끔 예전 캐시 때문에 최신 코드가 반영되지 않는 것처럼 보일 때가 있습니다. 그럴 땐
> `docker build --no-cache`로 캐시를 완전히 무시하고 처음부터 다시 빌드할 수 있습니다.

- 제출 위치: LMS 과제 게시판 (자세한 양식은 `10_과제제출/3주차_과제제출양식.md` 참고)

  하지 않아도 괜찮습니다.

  독립적으로도 제출 가능합니다.
