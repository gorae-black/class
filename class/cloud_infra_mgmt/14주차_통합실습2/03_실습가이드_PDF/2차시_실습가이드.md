# 14주차 2차시 실습가이드

## 개요

ApacheBench(`ab`)로 실제 트래픽 폭주 상황을 흉내내어, 지난 1차시에 설정한 HPA가 정말로
Pod를 늘리는지 직접 확인합니다. 단, 요청당 실제 연산이 거의 없는 앱은 부하를 줘도 CPU
사용률이 0%에 머무를 수 있다는 **검증된 함정**이 있으므로, 오늘은 챗봇 응답 로직에 연산을
추가한 뒤 부하 테스트를 진행합니다.

- 소요시간: 50분 (개념 설명 20분 + VM 실습 25분 + 결과 정리 5분)
- 실습 환경: VM 전용 (Killercoda 없음)
- 전제조건: 1차시에 설정한 HPA와 chatbot Deployment가 그대로 남아있어야 합니다.

## VM 실습

### 1. 챗봇 응답 로직에 연산 추가 후 배포

`app.py`의 응답 함수 안에 문자열 처리를 반복하는 코드를 몇 줄 추가합니다(예: 특정 연산을
N번 반복). 요청 하나당 실제로 CPU를 사용하는 시간이 생겨야 부하가 몰릴 때 사용률이 눈에
띄게 오릅니다.

코드를 수정한 뒤에는 12~13주차에 배운 파이프라인을 그대로 활용합니다.

```
git push origin main
```

파이프라인이 자동으로 배포할 때까지 기다렸다가, 새 버전이 반영됐는지 확인합니다.

### 2. 관찰용 터미널 두 개 준비

다른 터미널 창 두 개를 열어서 각각 아래 명령을 실행해 실시간으로 띄워둡니다.

```
kubectl get pods -w
```

```
kubectl get hpa -w
```

### 3. 부하 테스트 실행

```
ab -n 10000 -c 100 http://$(minikube service chatbot --url)/
```

`-n 10000`은 총 요청 수, `-c 100`은 동시성(동시 연결 수)을 뜻합니다.

> 2 vCPU 환경에서 VM이 너무 느려지면 `-c` 값을 100에서 30~50 정도로 낮춰서 실행해보세요.
> 목표는 극한의 부하가 아니라 '스케일업이 관찰될 정도'의 부하입니다.

### 4. 스케일업 관찰

부하를 주는 동안 `kubectl get hpa -w` 화면을 지켜봅니다. TARGET 항목의 CPU %가 점점
올라가는 것을 볼 수 있습니다. 목표치(50%)를 넘으면 REPLICAS가 1 → 2 → 3처럼 늘어나는
순간이 옵니다. 이 순간을 놓치지 말고 캡처하세요.

동시에 `kubectl get pods -w` 화면에서도 새로운 chatbot Pod가 추가로 생성되는 것을 확인할
수 있습니다.

> REPLICAS가 반드시 max(5)까지 다 늘어나야 하는 것은 아닙니다. 목표치를 넘는 순간 1개
> 이상 늘어나는 것만 확인되면 충분합니다.

## 제출 안내

아래 세 화면을 캡처하여 제출합니다.

1. `ab` 실행 결과(Requests per second 등 통계)
2. `kubectl get hpa`에서 REPLICAS가 늘어난 순간의 화면 (예: 1/1 → 3/5)
3. `kubectl get pods`에서 chatbot Pod가 여러 개로 늘어난 화면

> **주의**: 다음 3차시 자가치유 실습도 오늘 만든 HPA와 chatbot Deployment 상태를 그대로
> 이어받습니다. **오늘 만든 HPA와 chatbot Deployment를 절대 지우지 마세요.**
