# 4주차 3차시 실습가이드
## Deployment로 Pod 자동 관리하기

## 개요

지난 시간에는 `kubectl run`으로 Pod를 하나씩 직접 실행했습니다. 그런데 이 방식은 Pod가 죽으면
아무도 다시 살려주지 않는다는 문제가 있습니다. 오늘은 '항상 몇 개가 떠 있어야 한다'를 선언하면
K8s가 알아서 유지해주는 **Deployment**를 배웁니다. 핵심은 '명령'이 아니라 '선언'이라는 점입니다 —
우리는 원하는 최종 상태만 말해주고, 그 상태를 유지하는 건 K8s가 알아서 합니다. 이 선언은 YAML
파일로 작성하며, 기본 구조는 `apiVersion`·`kind`·`metadata`·`spec` 네 부분입니다. 오늘은 이
YAML을 직접 작성해서 클러스터에 배포하고, Pod 2개가 자동으로 만들어지는 과정을 눈으로 지켜봅니다.

- 소요시간: 개념 설명 25분 + Killercoda 실습 15분 + VM 과제 안내 5분 + 결과 제출 5분 (총 50분)
- 4주차의 마지막 시간입니다. Deployment는 내부적으로 ReplicaSet을 만들어 Pod 개수를 계속 감시하고,
  Pod 하나가 죽으면 즉시 새 Pod를 만들어 다시 채웁니다.

## Part A. Killercoda 실습

LMS > 4주차 > `05_Killercoda_링크`에 있는 3차시 링크로 접속한 뒤, 아래 순서대로 진행하세요.

> 이 세션에는 **60분 제한**이 있습니다. 중간에 끊기면 LMS 링크로 다시 접속해 이어서 진행하면 됩니다.

### Step 1. 노드 확인 (복습)

본격적인 실습에 앞서, 지난 시간 복습으로 `kubectl get nodes`를 한 번 실행해봅니다.

```
kubectl get nodes
```

**실행 결과 예시**

```
NAME           STATUS   ROLES           AGE   VERSION
controlplane   Ready    control-plane   12m   v1.30.1
```

노드가 `Ready` 상태로 정상 표시되면, 지난 시간 배운 클러스터가 그대로 잘 떠 있다는 뜻입니다.

### Step 2. deployment.yaml 작성하기

`replicas: 2`(항상 2개 유지)와 `nginx` 이미지를 선언하는 `deployment.yaml` 파일을 작성합니다.
아래 명령어를 그대로 실행하면 해당 내용으로 파일이 만들어집니다.

```
cat <<'EOF' > deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: nginx
        image: nginx
EOF
cat deployment.yaml
```

**실행 결과 예시**

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: nginx
        image: nginx
```

`cat deployment.yaml`로 방금 만든 파일 내용을 확인합니다. `apiVersion: apps/v1`, `kind: Deployment`,
`metadata`(이름 myapp), `spec`(replicas 2, nginx 이미지) 네 부분이 그대로 들어있는지 확인하세요.
YAML에서 제일 중요한 건 들여쓰기(스페이스 칸 수)입니다. 오늘은 위 템플릿을 그대로 복사해서 이름이나
replicas 숫자만 바꿔보는 것부터 시작하면 됩니다.

### Step 3. Deployment 배포하기

`kubectl apply -f {파일명}`으로 이 YAML 파일을 클러스터에 적용(배포)합니다.

```
kubectl apply -f deployment.yaml
```

**실행 결과 예시**

```
deployment.apps/myapp created
```

`created` 메시지가 보이면, K8s에게 "myapp이라는 이름으로 nginx Pod가 항상 2개 떠 있어야 한다"는
선언이 정상적으로 전달된 것입니다. 실제로 Pod가 만들어지는 과정은 다음 단계에서 확인합니다.

### Step 4. Pod가 생성되는 과정 관찰하기

`kubectl get pods -w`의 `-w`(watch)는 결과를 한 번만 보여주고 끝내는 게 아니라, 상태가 바뀔 때마다
새 줄로 계속 보여주는 옵션입니다. Pod 2개가 만들어지는 과정을 실시간으로 지켜봅니다.

```
kubectl get pods -w
```

**실행 결과 예시**

```
NAME                     READY   STATUS              RESTARTS   AGE
myapp-6b9f8c9d4c-abcde   0/1     ContainerCreating   0          2s
myapp-6b9f8c9d4c-fghij   0/1     ContainerCreating   0          2s
myapp-6b9f8c9d4c-abcde   1/1     Running             0          6s
myapp-6b9f8c9d4c-fghij   1/1     Running             0          8s
```

Pod 이름이 방금 만든 `mypod`처럼 고정된 이름이 아니라 `myapp-{랜덤문자}` 형태로 자동 생성된 것을
눈여겨보세요 — Deployment가 대신 이름을 지어 관리하기 때문입니다. 두 Pod 모두 `ContainerCreating` →
`Running`으로 바뀌고, 최종적으로 2개 모두 `1/1 Running` 상태가 되면 성공입니다. 이 명령은 스스로
끝나지 않으니, 확인이 끝나면 `Ctrl + C`로 빠져나오세요.

여기까지가 오늘의 Killercoda 실습입니다. 수고하셨습니다!

## Part B. 개인 VM 실습 (필수 제출)

개인 로컬 VM(cloud-lab)에서 진행합니다.

1. 클러스터를 켭니다.

   ```
   minikube start
   ```

2. Killercoda에서 작성한 것과 같은 `deployment.yaml`을 (Step 2와 동일한 내용으로) 작성하고
   배포합니다.

   ```
   kubectl apply -f deployment.yaml
   ```

3. Pod 2개가 `Running` 상태인지 확인합니다.

   ```
   kubectl get pods
   ```

4. **(자가치유 맛보기)** 여기서 하나만 더 해봅니다. 아래 명령으로 Pod 하나를 강제로 지워보세요
   (`{파드 이름}`은 위 결과에서 확인한 실제 Pod 이름 중 하나로 바꿔서 입력합니다).

   ```
   kubectl delete pod {파드 이름 중 하나}
   ```

   그리고 `kubectl get pods`를 다시 실행해보면 — 신기하게도 다시 2개로 돌아와 있을 겁니다!

   ```
   kubectl get pods
   ```

   이것이 바로 오늘 배운 '선언적 관리'가 실제로 작동하는 모습입니다. 원리는 7주차 '자가치유'
   시간에 자세히 다루니, 오늘은 이런 현상이 있다는 것만 확인해두면 충분합니다.
