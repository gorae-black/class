# 4주차 2차시 실습가이드
## Pod — K8s의 가장 작은 단위

## 개요

K8s는 컨테이너를 '직접' 다루지 않고, **Pod**라는 단위로 한 번 감싸서 다룹니다. Pod 안에는 보통
컨테이너가 1개 들어가지만 필요하면 여러 개를 넣을 수도 있고, 같은 Pod 안의 컨테이너들은 네트워크(IP
주소)와 저장 공간을 서로 공유합니다. 오늘부터 진짜 `kubectl` 명령어를 손으로 쳐보기 시작합니다.
`kubectl run`으로 Pod를 실행하고, `kubectl get pods`·`kubectl describe pod`·`kubectl logs`로 상태를
점검하는 것이 오늘의 목표입니다.

- 소요시간: 개념 설명 25분 + Killercoda 실습 15분 + VM 과제 안내 5분 + 결과 제출 5분 (총 50분)
- 오늘 배우는 다섯 개의 기본 명령어: `kubectl run`, `kubectl get pods`, `kubectl describe pod`,
  `kubectl logs`, `kubectl delete pod` (Docker에서 배운 run/ps/logs/rm과 거의 비슷한 구조입니다)

## Part A. Killercoda 실습

LMS > 4주차 > `05_Killercoda_링크`에 있는 2차시 링크로 접속한 뒤, 아래 순서대로 진행하세요.

> **⚠️ 참고: 이 실습 환경은 개인 VM(minikube)과 노드 구성이 다릅니다**
>
> 1차시와 같은 이유로 이 환경은 **Control Plane 1대 + Worker Node 1대**로 구성되어 있습니다(개인
> VM의 minikube는 노드 1대). 그래서 아래 실습에서 `kubectl describe pod`로 확인해보면, 이 Pod는
> Worker Node인 `node01`에 배치됩니다 — 일반 Pod는 '두뇌' 역할인 Control Plane이 아니라 '일꾼'
> 역할인 Worker Node에 배치되기 때문입니다(1차시에서 배운 역할 분담이 실제로 적용된 예시입니다).
> 개인 VM에서는 노드가 1대뿐이라 그 노드 하나에 배치됩니다.
>
> 이 세션에는 **60분 제한**이 있습니다. 중간에 끊기면 LMS 링크로 다시 접속해 이어서 진행하면 됩니다.

### Step 1. 첫 Pod 실행하기

`kubectl run {이름} --image={이미지}`로 Pod 하나를 즉석에서 실행합니다. Docker에서 배운
`docker run`과 거의 같은 구조입니다.

```
kubectl run mypod --image=nginx
```

**실행 결과 예시**

```
pod/mypod created
```

`created` 메시지가 보이면 K8s에게 "mypod라는 이름으로 nginx 이미지를 쓰는 Pod를 만들어라"는 요청이
정상적으로 접수된 것입니다.

### Step 2. Pod 상태 확인하기

`kubectl get pods`로 지금 떠 있는 Pod 목록과 상태를 확인합니다.

```
kubectl get pods
```

**실행 결과 예시**

```
NAME     READY   STATUS    RESTARTS   AGE
mypod    1/1     Running   0          10s
```

STATUS가 `Running`이면 정상입니다. 만약 방금 실행한 직후라 `ContainerCreating`처럼 아직 준비 중인
상태로 보인다면, 몇 초 기다렸다가 같은 명령어를 다시 실행해보세요 — 이미지를 받아오는 중이라 그런
것이니 "안 됐다"고 오해하지 않아도 됩니다.

### Step 3. Pod 상세 정보 확인하기

`kubectl describe pod {이름}`으로 이 Pod의 상세 상태와 무슨 일이 있었는지(이벤트), 그리고 어느
노드에 배치됐는지 확인합니다.

```
kubectl describe pod mypod
```

**실행 결과 예시**

```
Name:             mypod
Node:             node01/172.30.1.3
Status:           Running
IP:               10.244.1.5
...
Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  30s   default-scheduler  Successfully assigned default/mypod to node01
  Normal  Pulled     29s   kubelet            Container image "nginx" already present on machine
  Normal  Created    29s   kubelet            Created container mypod
  Normal  Started    29s   kubelet            Started container mypod
```

결과가 굉장히 길게 나오는 것이 정상입니다. 지금은 `Node` 항목(이 Pod가 어느 노드에 배치됐는지)과
맨 아래 `Events` 섹션(Scheduled → Pulled → Created → Started 순서로 잘 진행됐는지) 정도만 눈여겨보면
충분합니다. `Node`가 `controlplane`이 아니라 `node01`인 것에 주목하세요.

여기까지가 오늘의 Killercoda 실습입니다. 수고하셨습니다!

## Part B. 개인 VM 실습 (필수 제출)

개인 로컬 VM(cloud-lab)에서 진행합니다.

1. 클러스터를 켭니다(지난 시간에 켜두셨다면 생략 가능).

   ```
   minikube start
   ```

2. Killercoda에서 한 것과 동일한 명령어를 순서대로 실행합니다.

   ```
   kubectl run mypod --image=nginx
   kubectl get pods
   kubectl describe pod mypod
   kubectl logs mypod
   ```

   `kubectl logs mypod`는 Killercoda 실습에서는 다루지 않았지만, 오늘 배운 다섯 개 기본 명령어 중
   하나로, mypod 컨테이너가 출력한 로그를 보여줍니다.

   minikube는 노드가 1대뿐이므로, `kubectl describe pod` 결과의 `Node` 항목이 Killercoda의
   `node01`과 다르게 minikube의 노드 이름(예: `minikube`)으로 나올 수 있습니다. 노드 이름이
   다르더라도 실행 과정과 원리는 동일합니다.
