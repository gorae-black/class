# 13주차 2차시 실습가이드

## 개요

1차시에서 그려본 전체 아키텍처를 오늘은 실제 Jenkinsfile 코드로 완성합니다. 핵심은 "Jenkins
컨테이너에서 kubectl을 직접 실행하면 minikube에 접속이 안 된다"는 검증된 사실과, 그 우회 방법인
`docker exec`를 정확히 이해하는 것입니다.

- 소요시간: 50분 (개념 설명 20분 + VM 실습 25분 + 결과 정리 5분, Killercoda 없음)

## VM 실습

### 0. 실습 시작 전 — Credential 먼저 등록하기

Deploy 단계에서 인증 오류로 막히지 않도록, 실습을 시작하기 전에 반드시 먼저 Jenkins 관리 화면의
**Credentials** 메뉴에서 Docker Hub 아이디와 비밀번호를 `dockerhub-cred`라는 ID로 등록해두세요.
12주차에 배운 `withCredentials`를 쓰는 이유가 바로 이것입니다 — Jenkinsfile 코드 안에는 비밀번호가
절대 그대로 적히지 않고, Jenkins가 안전하게 저장해둔 값을 실행 시점에만 주입합니다.

### 1. 챗봇 프로젝트를 GitHub에 push

`app.py`, `Dockerfile`, `deployment.yaml`로 구성된 챗봇 프로젝트를 GitHub 저장소에 push합니다.

### 2. minikube에 chatbot Deployment 최초 1회 배포

`kubectl apply`로 minikube에 `chatbot` Deployment를 최초 1회 배포해둡니다.

### 3. 왜 kubectl을 Jenkinsfile에서 바로 실행하면 안 되는가

Jenkins는 Docker 컨테이너로 떠 있고, minikube도 별도의 Docker 컨테이너로 떠 있습니다. Jenkinsfile에서
kubectl을 곧바로 실행하면, 별도 Docker 네트워크와 IP 충돌 문제로 minikube 클러스터에 접속이 안
됩니다(이미 검증된 결과). 그래서 11주차에 Jenkins를 설치할 때 마운트했던 `docker.sock`을 이용해서,
minikube 컨테이너 **안**에 이미 들어있는 kubectl(및 인증 정보 `admin.conf`)을 `docker exec`로 그대로
실행하는 방식을 씁니다.

### 4. Jenkinsfile 4단계 작성

Checkout + Build + Push + Deploy 4단계가 모두 담긴 Jenkinsfile로 Pipeline Job을 만듭니다.

Build와 Push 단계는 12주차에 배운 문법과 거의 동일합니다.

```groovy
stage("Build") {
  steps { sh "docker build -t {id}/chatbot:${BUILD_NUMBER} ." }
}
stage("Push") {
  steps {
    withCredentials([usernamePassword(credentialsId:"dockerhub-cred",
      usernameVariable:"USER", passwordVariable:"PASS")]) {
      sh "echo $PASS | docker login -u $USER --password-stdin"
      sh "docker push {id}/chatbot:${BUILD_NUMBER}"
    }
  }
}
```

`${BUILD_NUMBER}`로 이미지에 버전 태그를 붙이고, `withCredentials`로 Docker Hub 비밀번호를 안전하게
사용합니다.

Deploy 단계는 오늘의 핵심인 `docker exec` 우회 방식입니다.

```groovy
stage("Deploy") {
  steps {
    sh 'docker exec minikube $(docker exec minikube sh -c "ls /var/lib/minikube/binaries/*/kubectl") \
        --kubeconfig=/etc/kubernetes/admin.conf \
        set image deployment/chatbot web={id}/chatbot:${BUILD_NUMBER}'
    sh 'docker exec minikube ... rollout status deployment/chatbot --timeout=120s'
  }
}
```

안쪽의 `docker exec minikube sh -c "ls ..."`가 먼저 실행되어 minikube 컨테이너 안의 kubectl 실제
경로를 찾아냅니다. 그 경로로 `--kubeconfig=/etc/kubernetes/admin.conf` 옵션을 주고 `set image` 명령을
실행해서, Deployment의 이미지를 방금 Push한 새 버전으로 교체합니다. `rollout status`는 이 교체(Rolling
Update)가 끝날 때까지 기다리는 명령입니다. `{id}` 부분은 본인 Docker Hub 아이디로 바꾸면 됩니다.
minikube 버전에 따라 kubectl 경로의 일부가 달라질 수 있어, 와일드카드(`*`)로 경로를 자동으로 찾아내는
방식을 씁니다.

### 5. 첫 수동 실행

Build Now로 첫 수동 실행을 해보고, Checkout·Build·Push·Deploy 4단계가 모두 성공(초록색)하는지
확인합니다.

## 제출 안내

- Stage View에서 Checkout·Build·Push·Deploy 4단계가 전부 성공한 화면을 캡처해서 제출합니다.
- `kubectl get pods`로 chatbot Pod가 새 이미지로 교체된 것을 확인해서 캡처합니다.
- 오늘 막혔던 부분이 있다면 무엇이었고 어떻게 해결했는지 간단히 기록해둡니다. 다음 3차시
  트러블슈팅 시간에 서로 도움이 됩니다.

### 참고 — 자주 겪는 문제

- Deploy 단계 오류는 대부분 다음 세 가지 순서로 확인합니다: ① Deployment 이름(`chatbot`)이나
  컨테이너 이름(`web`)이 실제 `deployment.yaml`과 다른 경우, ② Docker Hub에 이미지가 실제로
  Push됐는지, ③ minikube가 실행 중인지(`minikube status`).
