# 6주차 1차시 — ConfigMap과 Secret 퀴즈 (OX·단답형 8문항)

- 범위: 6주차 1차시(ConfigMap과 Secret)
- 형식: OX 5문항 + 단답형 3문항
- 용도: LMS 자동채점 퀴즈. 수업 중 함께 풀고 바로 정답·해설을 확인합니다.

---

## OX 문제 (1~5번)

**1.** 이미지 안에 설정값을 하드코딩해두면, 값을 하나 바꿀 때마다 이미지를 다시 빌드해야 한다. ( )

**2.** Secret은 값이 Base64로 인코딩되어 저장되는데, 이 인코딩 자체가 암호화이므로 그것만으로도
충분히 안전하다. ( )

**3.** 로그 레벨, API 서버 주소처럼 민감하지 않은 설정값은 ConfigMap으로 관리하는 것이 일반적이다.
( )

**4.** Secret 값을 진짜로 안전하게 지키려면, Base64 인코딩보다 '누가 접근할 수 있는가'를 관리하는
권한 설정이 더 중요하다. ( )

**5.** ConfigMap이나 Secret의 값을 변경하면, 이미 실행 중인 Pod에도 기본적으로 즉시 자동 반영된다.
( )

## 단답형 문제 (6~8번)

**6.** ConfigMap을 만들 때 사용하는 명령어의 기본 형태를 쓰세요. (예: `kubectl create configmap
{이름} ...`)

**7.** `--from-literal`처럼 key=value를 하나씩 지정하는 대신, 설정 파일 전체를 통째로 ConfigMap으로
만들고 싶을 때 사용하는 옵션은 무엇인가요?

**8.** DB 비밀번호, API 키처럼 민감한 정보를 저장할 때 ConfigMap 대신 사용하는 K8s 오브젝트는
무엇인가요?

---

## 정답 및 해설

| 번호 | 정답 | 해설 |
|---|---|---|
| 1 | O | 하드코딩된 설정값을 바꾸려면 이미지를 다시 빌드해야 하고, 개발·운영 환경마다 다른 설정을 쓰기도 어렵다. 그래서 ConfigMap·Secret으로 설정값을 이미지 밖에 분리해 관리한다. |
| 2 | X | Base64는 그냥 인코딩 방식이라서 누구나 디코딩할 수 있다. **암호화가 아니다.** |
| 3 | O | 로그 레벨, API 서버 주소, 최대 연결 수처럼 민감하지 않은 설정값에는 ConfigMap을 주로 사용한다. |
| 4 | O | 진짜 보안은 '이 Secret에 누가 접근할 수 있는가'를 관리하는 권한 설정으로 확보한다. Base64 인코딩 자체는 보안 수단이 아니다. |
| 5 | X | 값을 바꿔도 기본적으로는 즉시 반영되지 않는다. 새 값이 반영되려면 Pod를 재시작해야 하는 경우가 많다. |
| 6 | `kubectl create configmap {이름} --from-literal=KEY=VALUE` | 이 형태로 key=value 쌍의 설정값을 담은 ConfigMap을 만든다. |
| 7 | `--from-file` | 설정 파일 전체를 그대로 ConfigMap으로 만들 때 사용하는 옵션이다. |
| 8 | Secret | Secret은 ConfigMap과 사용법이 거의 같지만, 값이 Base64로 인코딩되고 접근 권한을 더 엄격하게 통제할 수 있어 DB 비밀번호, API 키, 인증서 같은 민감한 정보에 사용한다. |
