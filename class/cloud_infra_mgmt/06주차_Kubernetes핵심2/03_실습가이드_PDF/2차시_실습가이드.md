# 6주차 2차시 실습가이드
## PV와 PVC로 데이터 지키기

## 개요

지난 시간에 설정값과 비밀번호를 코드에서 분리하는 법을 배웠습니다. 오늘은 또 다른 중요한 문제를
다룹니다. Pod를 지우거나 재시작하면 그 안의 데이터는 어떻게 될까요? Pod도 결국 컨테이너를 감싸고
있는 것이라서, 컨테이너를 지우면 데이터도 함께 사라지는 문제를 그대로 가지고 있습니다. 게다가
Deployment는 Pod가 죽으면 자동으로 새 Pod를 만들어주는데, 그때마다 데이터가 초기화된다면
데이터베이스 같은 서비스에는 치명적입니다. 그래서 K8s는 Pod의 생명주기와 무관하게 데이터를
보관하는 **PV(PersistentVolume)**와 **PVC(PersistentVolumeClaim)**를 제공합니다.

- 소요시간: 개념 설명 25분 + Killercoda 실습 15분 + VM 과제 안내 5분 + 결과 제출 5분 (총 50분)
- 핵심 개념: **PV**는 실제로 존재하는 저장공간 그 자체이고, **PVC**는 "이런 저장공간이 필요해"라고
  요청하는 요청서입니다. Pod는 PVC를 통해서 PV에 연결되므로, 실제 저장공간이 어디에 있는지 직접
  알 필요가 없습니다. 오늘은 가장 간단한 방식인 **hostPath**(노드의 특정 디렉토리를 PV로 그대로
  사용하는 방식, 2주차에 배운 Bind Mount와 원리가 비슷함)로 직접 PV와 PVC를 만들어봅니다.
- **매우 중요**: 오늘 만든 PV와 PVC는 **지우지 말고 그대로 남겨두세요.** 다음 3차시에서 바로 이
  PVC를 실제 MySQL Pod에 연결합니다.

## Part A. Killercoda 실습

LMS > 6주차 > `05_Killercoda_링크`에 있는 2차시 링크로 접속한 뒤, 아래 순서대로 진행하세요.

> 이 세션에는 **60분 제한**이 있습니다. 실습 중 시간이 종료되어도 당황하지 마세요 — 중간에 끊기면
> LMS 링크로 다시 접속해 이어서 진행하면 됩니다.
>
> **다음 차시에서 계속 사용합니다**: 오늘 만든 PV와 PVC는 다음 3차시에서 실제 MySQL Pod에 연결할
> 예정이니, 실습이 끝나도 절대 지우지 마세요.

### Step 1. PV(PersistentVolume) 만들기

hostPath는 노드(VM)의 특정 디렉토리를 PV로 그대로 사용하는 방식입니다. `/data/mysql` 디렉토리를
1Gi 용량의 PV로 등록해보겠습니다.

```
cat << 'EOF' > pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: mysql-pv
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  hostPath:
    path: /data/mysql
EOF
kubectl apply -f pv.yaml
```

**실행 결과 예시**

```
persistentvolume/mysql-pv created
```

`created` 메시지가 나오면 PV가 정상적으로 만들어진 것입니다.

### Step 2. PV 상태 확인하기

`kubectl get pv`로 방금 만든 PV의 상태를 확인합니다.

```
kubectl get pv
```

**실행 결과 예시**

```
NAME       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   AGE
mysql-pv   1Gi        RWO            Retain           Available           <unset>        10s
```

STATUS가 `Available`이면, 아직 이 PV를 사용하겠다는 PVC가 없어서 대기 중인 정상 상태입니다.

### Step 3. PVC(PersistentVolumeClaim) 만들기

이제 이 PV가 제공하는 만큼의 storage를 요청하는 PVC를 작성합니다. Pod는 이 PVC를 통해서 PV에
연결됩니다 — 실제 저장공간이 어디에 있는지 직접 알 필요가 없습니다.

```
cat << 'EOF' > pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
EOF
kubectl apply -f pvc.yaml
```

**실행 결과 예시**

```
persistentvolumeclaim/mysql-pvc created
```

`created` 메시지가 나오면 PVC가 정상적으로 만들어진 것입니다.

### Step 4. PV·PVC가 Bound 되었는지 확인하기

`kubectl get pv`와 `kubectl get pvc`를 실행해서 PV와 PVC가 서로 연결(Bound)되었는지 확인합니다.

```
kubectl get pvc
```

**실행 결과 예시**

```
NAME        STATUS   VOLUME     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
mysql-pvc   Bound    mysql-pv   1Gi        RWO                           5s
```

```
kubectl get pv
```

**실행 결과 예시**

```
NAME       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM               STORAGECLASS   AGE
mysql-pv   1Gi        RWO            Retain           Bound    default/mysql-pvc                  15s
```

두 명령 모두 STATUS가 **Bound**로 나오면 성공입니다. 만약 `Pending`이라면 PV와 PVC의 조건(용량,
접근 모드)이 서로 맞지 않는 경우가 대부분이니 `kubectl describe pvc mysql-pvc`로 Events를
확인해보세요.

여기까지가 오늘의 Killercoda 실습입니다. 수고하셨습니다!

## Part B. 개인 VM 실습

개인 로컬 VM(cloud-lab)에서도 동일하게 pv.yaml, pvc.yaml을 작성하고 적용해봅니다.

1. VM에 접속한 뒤, 필요하다면 클러스터를 켭니다.

   ```
   minikube start
   ```

2. Killercoda에서 작성한 것과 같은 내용으로 `pv.yaml`을 작성하고 적용합니다.

   ```
   cat << 'EOF' > pv.yaml
   apiVersion: v1
   kind: PersistentVolume
   metadata:
     name: mysql-pv
   spec:
     capacity:
       storage: 1Gi
     accessModes:
       - ReadWriteOnce
     hostPath:
       path: /data/mysql
   EOF
   kubectl apply -f pv.yaml
   ```

3. 같은 방식으로 `pvc.yaml`을 작성하고 적용합니다.

   ```
   cat << 'EOF' > pvc.yaml
   apiVersion: v1
   kind: PersistentVolumeClaim
   metadata:
     name: mysql-pvc
   spec:
     accessModes:
       - ReadWriteOnce
     resources:
       requests:
         storage: 1Gi
   EOF
   kubectl apply -f pvc.yaml
   ```

4. `kubectl get pv`, `kubectl get pvc`로 STATUS가 **Bound**로 나오는지 확인합니다.

   ```
   kubectl get pv
   kubectl get pvc
   ```

**꼭 기억하세요**: 오늘 VM에서 만든 이 `mysql-pv`, `mysql-pvc`는 지우지 말고 그대로 남겨두세요.
다음 3차시에서 바로 이 PVC를 실제 MySQL Pod에 연결합니다.
